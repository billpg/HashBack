HashBack: Server-to-Server Authentication by Published Hash

Abstract

HashBack is a two-step authentication exchange carried over HTTPS/TLS that allows one HTTP server to authenticate another, without either party holding a long-term shared secret, bearer token, or private key. A caller proves its identity by publishing a short cryptographic hash on a website it controls; the recipient of a request fetches that hash over a second, independent HTTPS connection and compares it against a value it calculates itself. If the two values match, the recipient is reassured that the caller is who it claims to be. This document describes the HashBack exchange, the format of the Authorization header it defines, and the security considerations that apply to implementations.¶

1. Introduction

A server that calls out to another server over the Internet typically needs some way to prove its identity: an API key, a bearer token, a shared secret, or a private key backing a client TLS certificate. Whichever form it takes, that credential has to be generated, distributed to the calling service, stored securely at both ends, and eventually rotated - all before the two services can exchange a single authenticated request.¶

HashBack removes the need for that long-term credential entirely. Instead, it relies on a property both parties already have if they are communicating over HTTPS at all: each side runs a TLS-secured web server that the other side can reach. HashBack uses this in a manner similar to a phone call placed to a trusted number and then immediately hung up so the other side can call back: the caller tells the recipient "I am the operator of this URL - call me back there to check", and publishes a value at that URL for the recipient to retrieve.¶

This is deliberately similar in spirit to the challenge exchange used by the Automatic Certificate Management Environment (ACME) [RFC8555], which validates control of a domain name by asking the requester to publish a token there ahead of a certificate being issued. HashBack applies the same "prove control of a URL" idea to general-purpose API authentication, and reduces the exchange to two HTTP transactions instead of three.¶

This document is an early, individual Internet-Draft. It has not been adopted by any IETF working group. It is published to invite review and comment ahead of a future submission for standardization.¶

2. Terminology and Notation

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

This document additionally uses the following terms:¶

Caller:
The party sending the HTTP request being authenticated. Also referred to as the client.¶
Recipient:
The party receiving and authenticating the HTTP request. Also referred to as the server.¶
Unus:
A 128-bit cryptographic-quality random value, encoded in Base64, included in every request to make its verification hash unpredictable. Equivalent in purpose to a cryptographic nonce. The name is the Latin word for "one" or "single".¶
Verify URL:
An HTTPS URL, under the Caller's control, where the Caller publishes the verification hash for a given request.¶
Verification hash:
The Base64-encoded, salted SHA-256 hash of a request's JSON object, as described in Section 6.¶
Fixed Salt:
A 32-byte value, fixed by this document and not secret, prepended to a request's bytes before hashing. See Section 6.¶

3. Protocol Overview

In outline, the Caller builds a JSON object describing the request it is about to make, including the URL where it will publish that object's hash. It sends this object, Base64-encoded, in the HTTP Authorization header of its request. Before or immediately after sending that request, it publishes the object's verification hash at the declared URL.¶

On receiving the request, the Recipient parses the Authorization header, applies its own policy checks (see Section 7), and then makes a separate HTTPS GET request to the Verify URL to retrieve the published hash. The Recipient computes the same hash itself from the bytes it received and compares the two values. If they match, the Recipient has confirmed that whoever controls the Verify URL endorses this specific request, and processes it accordingly.¶

Two independent HTTPS connections are used: the original request, and the Recipient's GET request to the Verify URL. Because TLS secures both connections, and because the published value is a hash of the specific request rather than a fixed shared secret, this exchange requires no pre-agreed credential beyond the Recipient knowing which range of Verify URLs belong to which Caller (see Section 4).¶

4. Prerequisite: Declaring a Verify URL Range

Before this exchange can take place, the Recipient MUST have a way to map an incoming Verify URL to a specific, known Caller identity. Exactly how this mapping is established and stored is outside the scope of this document (it might be an entry in a configuration file, a row in a database populated through a self-service web portal, or a value baked into deployment configuration), but the range of URLs accepted for any one Caller MUST be narrow enough that no other party could plausibly publish content there.¶

A single fixed URL, or a URL varying only in a query string parameter or a restricted path segment, is appropriate. A URL prefix that could allow the Caller's other users to publish arbitrary content (for example, a path serving user comments or a public wiki) is not, because it would let an unrelated party impersonate the Caller by publishing a hash of their own choosing under that same prefix.¶

Examples of acceptable and unacceptable declarations:¶

Table 1: Verify URL range examples
Pattern Acceptable? Reason
https://example.com/hashback?id=* Yes Single fixed path, varying only in a query parameter
https://example.com/hashback/*.txt Yes Single restricted folder, no further subfolders
http://example.com/hashback/* No Not protected by TLS
https://example.com/* No Too broad; covers content the Caller does not control
https://example.com/blog/* No May allow third-party comments

5. The Authorization Header

The Caller authenticates its request using the HTTP Authorization request header field, using the auth-scheme token HashBack:¶

Authorization = "HashBack" 1*SP token68
¶

where token68 is as defined by Section 11.3 of [RFC9110]. The token68 value MUST be the standard Base64 encoding (Section 4 of [RFC4648], including padding, and without line breaks) of a JSON object, encoded as UTF-8, described below. (Line breaks shown in examples in this document are for presentation only and are not part of the header value.)¶

5.1. JSON Object Properties

The JSON object MUST be a JSON object, as defined by [RFC8259], containing exactly the following members. All values are strings unless stated otherwise. All members are REQUIRED.¶

Version:
A string identifying the version of this exchange in use. This revision of this exchange is identified by the string "BILLPG_DRAFT_4.2", for compatibility with the reference implementation published alongside earlier drafts of this document. A future revision of this document, once adopted as an IETF work item, is expected to define a new version string of the form "RFC_NNNN", where NNNN is the number ultimately assigned to that RFC.¶
Host:
The full domain name of the Recipient being called in this request. Because intermediaries such as load balancers and content delivery networks can rewrite the HTTP Host header, this property carries an authoritative copy included in the hashed material, so there is no ambiguity about which name the Caller intended. The Recipient MUST reject any request whose Host property does not match one of its own recognized names, including generic names such as "localhost" that belong to no specific service. See Section 10.2.¶
Now:
The current UTC time, expressed as an integer number of seconds since the start of 1970 (a Unix timestamp). Values MUST use an integer type wider than 32 bits, so that this mechanism continues to function beyond the year 2038. The Recipient SHOULD reject a request if this value is too far from its own clock; this document does not mandate a specific threshold, leaving that to the Recipient's own configuration.¶
Unus:
128 bits of cryptographic-quality randomness, Base64-encoded including any trailing "=" padding. Every other property of this JSON object is potentially predictable to an attacker; the security of this exchange depends on this value, and only this value, being unpredictable (see Section 10.3). A Caller MUST NOT reuse a Unus value across requests. A Recipient SHOULD reject any request reusing a Unus value it has already seen within its configured Now tolerance window.¶
Verify:
An https:// URL, belonging to the Caller, from which the Recipient can retrieve the verification hash with an HTTP GET request. This URL MUST fall within a range the Recipient has already associated with a specific Caller identity, per Section 4.¶

If either the Host or Verify property would otherwise contain a non-ASCII internationalized domain name, that name MUST be normalized and represented either as literal UTF-8 or using JSON's \u escape notation, and MUST NOT use the ToASCII ("xn--") form.¶

For example, the following JSON object:¶

{
    "Version": "BILLPG_DRAFT_4.2",
    "Host": "server.example",
    "Now": 529297200,
    "Unus": "Rpgt4Fc5nMDq14LOps/hYQ==",
    "Verify": "https://client.example/api/hashback?id=502542886"
}
¶

is Base64-encoded and sent as the following Authorization header field:¶

Authorization: HashBack
 eyJWZXJzaW9uIjoiQklMTFBHX0RSQUZUXzQuMiIsIkhvc3QiOiJzZXJ2ZXIuZXhhbXBs
 ZSIsIk5vdyI6NTI5Mjk3MjAwLCJVbnVzIjoiUnBndDRGYzVuTURxMTRMT3BzL2hZUT09
 IiwiVmVyaWZ5IjoiaHR0cHM6Ly9jbGllbnQuZXhhbXBsZS9hcGkvaGFzaGJhY2s/aWQ9
 NTAyNTQyODg2In0=
¶

6. Verification Hash Calculation and Publication

Both the Caller and the Recipient compute the verification hash the same way, from the same bytes: the exact UTF-8 byte sequence that was (or will be) Base64-decoded from the Authorization header. The hash MUST be computed as follows:¶

  1. Concatenate the 32-byte Fixed Salt below with the UTF-8 bytes of the JSON object, salt first.¶
  2. Compute the SHA-256 digest ([RFC6234]) of the concatenated bytes.¶
  3. Base64-encode the 32-byte digest, including any trailing "=" padding.¶

The Fixed Salt is the following 32 bytes:¶

48,106,239,61,141,188,122,117,
71,242,89,164,154,89,44,47,
20,42,34,245,250,230,139,30,
56,240,40,168,35,184,92,252
¶

equivalently, in Base64: MGrvPY28enVH8lmkmlksLxQqIvX65oseOPAoqCO4XPw=, or in hexadecimal: 306AEF3D8DBC7A7547F259A49A592C2F142A22F5FAE68B1E38F028A823B85CFC.¶

The Fixed Salt is NOT a secret. Its only purpose is to ensure a HashBack verification hash cannot be confused with, or produced by, an unrelated general-purpose hashing service, since that service would not have prepended this same value. It was generated using PBKDF2 with the following parameters, provided here for transparency and reproducibility rather than as part of the algorithm implementers need to run:¶

Password:
"HashBack is dedicated to my Treacle."¶
Salt:
"I love you to the moon and back."¶
Hash algorithm:
SHA-512¶
Iterations:
477708¶
Output:
256 bits¶

The expected verification hash for the example request in Section 5.1 is /+Zc/xVCVgnnfC69tEybe2TAluOk21ScdystX0/1Ayk=.¶

Once computed, the Caller MUST publish the verification hash at the Verify URL before, or without excessive delay after, sending the authenticated request, so that it is available by the time the Recipient fetches it. The response to a GET request for the Verify URL MUST:¶

  • Use the 200 OK status code;¶
  • present a valid TLS certificate for the Verify URL's host;¶
  • not be a redirect of any kind - the Recipient MUST NOT follow redirects when fetching this URL, both because the Caller is expected to know the final URL when building the request and to avoid exposing the Recipient to server-side request forgery (SSRF) risk; and¶
  • return, as its entire body, a single line of text containing the Base64-encoded verification hash in ASCII, with no end-of-line sequence or a single CR, LF, or CRLF sequence following it.¶

The Recipient compares the hash it downloads against the hash it computes itself from the bytes it decoded from the Authorization header. If the Recipient cannot retrieve a matching hash - because of a network failure, an unexpected status code, a certificate problem, or a mismatched value - it MUST treat the request as unauthenticated and respond with a suitable HTTP error, with enough detail in the response to help a reasonably experienced developer correct the problem.¶

7. Recipient Processing

On receiving a request bearing a HashBack Authorization header, the Recipient MUST perform the following checks, in any order, before treating the request as authenticated:¶

  1. The request arrived over HTTPS, the Authorization header uses the HashBack auth-scheme, and its token68 value Base64-decodes to a well-formed JSON object with all the members listed in Section 5.1.¶
  2. The Version property is one this Recipient implements.¶
  3. The Host property is a name this Recipient recognizes as itself (see Section 10.2).¶
  4. The Now property is within the Recipient's configured tolerance of its own clock.¶
  5. The Unus property is well-formed and, if replay protection is configured, has not already been seen.¶
  6. The Verify property is an HTTPS URL the Recipient can map to a specific, known Caller identity, per Section 4.¶
  7. The verification hash retrieved from the Verify URL matches the hash the Recipient computes itself, per Section 6.¶

If every check passes, the Recipient treats the request as authenticated as the Caller identity associated with the Verify URL, and proceeds to process the request that carried the header. If any check fails, the Recipient MUST NOT process the request and SHOULD respond with an HTTP 4xx status code.¶

8. Advertising Support via WWW-Authenticate

A Recipient rejecting an unauthenticated request with a 401 response MAY advertise support for this exchange using a WWW-Authenticate response header field Section 11.6.1 of [RFC9110] whose auth-scheme is HashBack. An optional realm auth-param MAY be present. An optional version auth-param, if present, MUST be a comma-separated list of Version values this Recipient accepts, most preferred first; a Caller SHOULD select a value from this list when building its next request. Absence of the version parameter does not imply that HashBack is unsupported.¶

HTTP/1.1 401 Unauthorized
WWW-Authenticate: HashBack realm="My_Wonderful_Realm"
 version="RFC1234,BILLPG_DRAFT_4.2,BILLPG_DRAFT_4.1"
¶

A Caller that already knows a Recipient supports HashBack MAY send the Authorization header on its first request, skipping this discovery step.¶

9. Repeated Requests

Every HashBack exchange requires a fresh JSON object, a freshly published verification hash, and therefore a second HTTPS round trip on the Recipient's side. This is inherently more expensive than reusing a bearer token, and this document intentionally does not define a token format or refresh mechanism to sit on top of it.¶

Implementations that need to authenticate many requests in succession are RECOMMENDED to run one HashBack exchange and then have the Recipient issue its own short-lived credential - for example, a bearer token or a Set-Cookie response header - that the Caller then presents for subsequent requests until it expires, at which point the HashBack exchange is repeated. The format, lifetime, and transport of that credential is outside the scope of this document.¶

10. Security Considerations

10.1. Dependency on TLS

This exchange depends entirely on the security properties of TLS for both HTTP transactions. It provides no security of its own against an attacker capable of defeating TLS - such as one holding a certificate improperly issued by a trusted certificate authority - beyond whatever precautions an implementation separately takes, such as maintaining its own restricted set of trusted certificate authorities or pinning certificates for known Callers.¶

10.2. Relay ("Pass-Along") Attacks

Without the Host property, a Recipient that is itself malicious, or that has been compromised, could take a valid request received from a genuine Caller and forward it unmodified to a third Recipient, which would retrieve the same verification hash and be fooled into believing it was talking directly to the original Caller. Because Host is included in the hashed material, a forwarded request would carry the wrong Host value for the third Recipient, and Section 7 requires that value be rejected. For this reason, a Recipient MUST reject any request whose Host property is not a name it recognizes as its own, including generic names such as "localhost" that could belong to any server.¶

10.3. Predictability of Request Contents

With the exception of Unus, every property of the JSON object described in Section 5.1 may be entirely predictable to an attacker without weakening this exchange. An attacker who can predict or observe a Verify URL and its published hash still cannot construct a valid request for a different Recipient, because doing so requires finding a JSON object - including a Unus value - that hashes to that same value, which is computationally infeasible against SHA-256. Implementations therefore MUST generate Unus using a cryptographically secure random number generator, and MUST NOT reuse a value.¶

10.4. Rationale for Publishing a Hash Rather Than a Token

An earlier design considered simply publishing a random value and including that same value directly in the request, without hashing. This does not work: it recreates the relay attack described in Section 10.2 without the Host binding being sufficient to stop it, since a malicious intermediate Recipient could republish an unmodified copy of the random value itself. Requiring the published value to be a hash of the entire request - including the intended Recipient's Host - ties the published proof to one specific request. Changing or reusing any part of that request changes the expected hash, and the forwarded copy will not satisfy an unrelated Recipient's own check.¶

10.5. Server-Side Request Forgery Considerations

Fetching a URL supplied in an incoming request carries the usual SSRF risks associated with any user-supplied URL fetch. Implementations SHOULD apply the same precautions they would to any other outbound fetch of caller-supplied data: resolving and validating the destination address before connecting, rejecting internal or loopback address ranges unless explicitly intended (for example, during local development), declining to follow redirects (see Section 6), and applying a request timeout.¶

10.6. Denial of Service Considerations

Because every incoming request with a HashBack header causes the Recipient to make a further outbound HTTPS request, a flood of fabricated Authorization headers could be used to exhaust a Recipient's outbound connection capacity, even though every one of those requests will ultimately fail verification. Implementations SHOULD apply a short connection and response timeout to the Verify URL fetch, and MAY track and rate-limit sources of requests that repeatedly fail verification.¶

A related concern is a malicious Verify URL that accepts the connection but never completes the response, tying up a connection on the Recipient for as long as it is willing to wait. A short, strictly enforced timeout on the Verify URL fetch mitigates this; the timeout only needs to be long enough for the expected response to arrive under normal network conditions.¶
