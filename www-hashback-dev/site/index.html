Trust without storing secrets.

HashBack gives services a simple way to prove identity over HTTPS using a two-step exchange and verification hashes. Instead of keeping long-lived passwords or API tokens in a vault, the caller and server can mutually reassure each other that the right party is present using the same TLS infrastructure they've already got.

From a simple analogy to a practical authentication mechanism

HashBack takes inspiration from a phone-call analogy: The caller knows who they are calling, but the recipient doesn't know who that call is coming from. But if the recipient can call that original caller back, they can be reassured that the caller is who they say they are.

Did you see what didn't happen? No-one needed a cryptographic key or secret token.

Now apply that concept to web authentication. The client knows, thanks to TLS, who they are connecting to, but the server doesn't know who that incoming connection is from. If the server can call the client back, this time the server knows, thanks again to TLS, that the client is who they say they are. The two connections in opposite directions complete the loop.

How the flow works

  1. The client prepares an authentication claim and calculates a verification hash.
  2. The client publishes that hash on a TLS-protected URL it controls.
  3. The server fetches the verification hash, confirms it matches, and accepts the request.

Why it matters

HashBack means you don't need to store and manage long-term shared secrets. Use your existing TLS infrastructure to build a more secure and manageable authentication system.
