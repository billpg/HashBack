An example HashBack session

Let's follow one request from the client's first thought to the server's final nod. Hashbert the Hedgehog will annotate the important bits, because authentication is easier to understand when someone points at the spiky details.

Step 01

Declare the verification URL range

Ahead of time, the client administrator registers the exact narrow HTTPS URL or folder where verification hashes will be published. The service uses this declaration to map the URL back to the client and must reject URLs outside it.

My hashes will be published at:
https://client.example/api/hashback?id=*

Hashbert says: "Choose a small patch of HTTPS ground that you control. A single doorway is splendid; handing over the whole house is a bit much, even for a hedgehog with a clipboard."

Step 02

Write the authentication JSON

When the client wants to make an authenticated request, it creates a fresh JSON claim. It names the protocol version, destination host, current UTC time, a unique random value, and the HTTPS URL where the server can retrieve the verification hash.

{
    "Version": "BILLPG_DRAFT_4.2",
    "Host": "server.example",
    "Now": 529297200,
    "Unus": "Rpgt4Fc5nMDq14LOps/hYQ==",
    "Verify": "https://client.example/api/hashback?id=502542886"
}

Hashbert says: "This claim is fresh, specific, and meant for one destination. The Unus value must be unpredictable and unique, so a stale claim cannot simply wander back in wearing a fake moustache."

Step 03

Hash the JSON and publish the result

The client encodes the JSON as UTF-8 bytes, combines those bytes with HashBack's fixed public salt, and calculates a SHA-256 hash. It Base64-encodes the result, then publishes that one-line value at the exact Verify URL from the JSON.

GET /api/hashback?id=502542886 HTTP/1.1
Host: client.example
 
HTTP/1.1 200 OK
Content-Type: text/plain
 
/+Zc/xVCVgnnfC69tEybe2TAluOk21ScdystX0/1Ayk=

Hashbert says: "The hash waits on the client's own HTTPS site. Nothing secret needs to live there forever; this value belongs to this one fresh claim and should be replaced for the next request."

Step 04

Make the HTTP request

The client Base64-encodes the JSON bytes and places that string in the HTTP Authorization header using the HashBack authentication scheme. The request can then carry its normal API method, path, and body.

POST /api/order HTTP/1.1
Host: server.example
Authorization: HashBack
    eyJWZXJzaW9uIjoiQklMTFBHX0RSQUZUXzQuMiIsIkhvc3QiOiJzZXJ2ZXIuZXhhbXBsZSIsIk5v
    dyI6NTI5Mjk3MjAwLCJVbnVzIjoiUnBndDRGYzVuTURxMTRMT3BzL2hZUT09IiwiVmVyaWZ5Ijoi
    aHR0cHM6Ly9jbGllbnQuZXhhbXBsZS9hcGkvaGFzaGJhY2s/aWQ9NTAyNTQyODg2In0=
Accept: application/json

Hashbert says: "The header carries the claim, not a permanent password. The server can decode it, but the proof still depends on the matching hash being available from the HTTPS URL you declared."

Step 05

Load the published hash

The server decodes the authorization claim, checks the version, host, timestamp, one-use value, and registered URL, then performs a separate HTTPS GET to the Verify URL supplied by the client.

GET https://client.example/api/hashback?id=502542886
 
Expected response body:
/+Zc/xVCVgnnfC69tEybe2TAluOk21ScdystX0/1Ayk=

Hashbert says: "Now the server is calling back. It follows only the pre-approved route, checks the TLS certificate, and expects one plain-text Base64 hash. No detours through suspicious bramble patches."

Step 06

Repeat the hash and confirm identity

The server repeats the same hashing process on the JSON bytes from the decoded header. If its result exactly matches the hash retrieved from the client's declared HTTPS location, the server can be reassured that the client controls that location and may process the request.

1. DecodeRead the JSON claim from the header.
2. RecalculateHash the claim with the fixed salt.
3. CompareAccept an exact match.

Hashbert says: "A matching result confirms control of the registered website. The server has not been handed a long-lived secret; it has checked a fresh proof from the right HTTPS location. That is a very satisfactory conclusion."
